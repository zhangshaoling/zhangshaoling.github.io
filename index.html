一句话定位

我在做的不是单个产品，而是一套能把想法变成程序、把程序变成长期运行系统的 AI runtime 作品集。

Language 让 thought = code = memory 成为可执行现实。
Infrastructure 让 Agent 能持续接任务、调用工具、自动交付。
Foundation 用 C 从 shell、malloc、database 一直走到 tiny OS。

三条主线

这些项目不是彼此孤立的仓库，而是在回答同一个问题：怎样构建一个真正可成长、可组合、可自我演化的 AI 系统？

1. Ku / Language Runtime

Ku 是一门 AI-native、自修改、自举方向的语言实验。它把 thought、code、memory 放在同一层语义上，希望把“程序”和“记忆”之间的边界压缩到最小。

self-hosting metaprogramming thought-as-code

2. Agent Infrastructure

我关心的不是一次性的 prompt，而是长期运行的 Agent：能巡航、能路由模型、能调用工具、能留下工作记忆，并且能把输出变成交付。

automation MCP tool orchestration

3. Systems Programming

CppLearning 是我的地基工程。从 shell、malloc、database、Lisp 到 tiny OS，我希望真正理解程序是怎么跑起来的，而不是永远停留在框架表层。

C runtime basics boot process

我现在在做什么

  • 继续推进 Ku 的自举路线，把语言从“可运行”推向“可自我承载”。
  • 把 Agent 自动化系统从一次性流程升级成可复用模板与基础设施。
  • 通过 CppLearning 补齐 runtime / memory / storage / boot 这条底层能力链。
  • 把项目表达升级成统一作品集，而不是分散的仓库说明。

我不是只想“把模型接进来”，而是想搭一整套能承载记忆、工具、执行与自我修正的运行时。

如果说普通应用是在调用模型，那么我更关心的是：模型之外，系统本身怎样成长。

为什么这些项目会串成一条线

看起来我同时在做语言、自动化、系统编程，其实它们在同一个方向上会合。

Language →

Ku 负责表达“思想、记忆、工具、计划”这些更贴近 Agent 的语义单元。

Infrastructure →

Hermes / gateway 负责让模型调用、任务调度、工具执行和交付链路真的跑起来。

Systems →

CppLearning 负责补齐底层理解，避免 runtime 设计永远漂浮在抽象层。
